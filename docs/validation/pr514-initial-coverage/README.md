# PR #514: 初期編成の同一計画内再登録

2026-10-30。WebKit修正head `5f74dd4` のCI #561では、hub-navigationは追加8件を含む58/58成功したが、initializationの保存失敗→再試行ケースが一軍捕手不足で失敗した。main `521d64b` と同じ既存処理に起因する追加修正として分離して記録する。

## 原因

[失敗CI](https://github.com/shotaro-hue/baseball-manager/actions/runs/40974171280) のtraceを確認した。初回保存失敗後に再試行したゲーム開始直後、ロッテ（teamId 9）は一軍28人・捕手2人、二軍37人・捕手4人で、二軍は試合可能だった。二塁に守備適性のある実在5選手は全員二軍・再登録待機10日。一軍には二塁適性のある選手がおらず、適性外の守備配置へフォールバックしていた。外国人枠の超過や試合中の負傷ではない。

`ensureRequiredFieldingCoverage()` は同じ編成計画で発生した降格の再呼出しを認める条件を持つ一方、その直後に、待機日数を持つ元の選手を `canAddToActiveRoster()` へ渡していた。この関数が待機中の選手を拒否するため、後続の待機解除処理へ到達できなかった。守備配置が修復されず、自然な守備配置を維持できる交代だけを認める捕手補充も止まった。

固定乱数seed 1099で同じ障害を再現した。この例では二塁適性のある実在4選手が全員同一計画内で降格し、一軍捕手が2人になった。CIの乱数列そのものを復元したものではないが、同じ判定の欠陥を再現する。

## 修正と範囲

同一計画内の再呼出しが許可され、正の待機日数を持ち、計画開始時の待機選手IDに含まれない場合だけ、待機日数0のコピーで候補の適格性を判定する。選ばれた選手の反映には従来の処理を使う。既存の育成・負傷・外国人枠・待機日数・守備配置の検証を緩めない。

共有の編成計画処理を直すため、ゲーム開始時に加え、通常の全自動編成で既に意図されていた同一計画内の守備要員再呼出しも機能する。以前から待機中だった選手は再登録しない。選手の追加、守備適性・能力の書換え、保存形式・FA処理・契約台帳・給与・予算の変更はない。既存セーブへのデータ移行も行わない。
