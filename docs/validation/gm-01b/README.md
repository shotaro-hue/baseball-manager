**今回の成果は、GM-01C/Dで使う未接続の共通基盤。ゲームでの給与控除・コーチ料金・予算配布・保存形式は変更していない。** #505の計算だけの状態から、契約履歴を残す台帳と年度別の審査へ進めた。新ルールの有効化、旧セーブ移行、実UI/CPUの確認、動的な係数選定は次工程。

## 1. 金額が消えない契約台帳

`contractLedger.js`の正本は、原契約・初期球団・効力日・取引IDと、移籍/増額/終了の境界記録だけ。毎試合の給与履歴や、別に更新する年次残高を持たない。在籍/支払球団/年俸レートと年度別負担は#505の月割り累計差分から導出する。

| 操作 | 記録・審査 |
|---|---|
| 新規/更改 | 契約開始/終了年度を維持。新規加入は7/31まで、更改は対象年度2/1から |
| 移籍 | 既存負担を売手へ残し、効力日からの負担を買手へ。契約期間は延長しない |
| 同日再移籍 | 中間球団のゼロ日区間は作らず、端数も増やさない |
| 年俸増額 | 変更前は旧額、変更後と将来年度は新額。原契約は保存。既存保証額の一方的減額は不可 |
| 保証付きの球団都合解雇 | 雇用を終えても残債は元球団の保証負担として残す。waive指定は拒否 |
| 本人引退/ポスティング | 残債をretain/waiveのどちらに合意したかを明示。経過負担は維持 |
| 再受信/再読込 | 同じ取引ID・同条件は同じ台帳を返し、異なる条件の使い回しは拒否 |
| 年度締め | 負担記録を削除せず、閉じた年度へ新しい取引を追加しない |

たとえば年俸1億円を2/1から負担し、7/1にA→B、7/16にBが保証解雇した場合、2026年はAの給与5,000万円、Bの給与484万円、Bの保証残債4,516万円。2027/2028年はBに各1億円の保証残債が残る。退団名簿だけを集計して残債を消す構造にしていない。

育成年俸240万円を7/16から420万円へ増額した例は、変更前132＋変更後190＝322万円。年俸差180万円だけを別に按分する方式とは端数が異なるため、各レートの期間を計算する。

`contractLiabilityRows`はcontractId/playerId/teamId/season/kind/amountManYenを返す。kindはsalaryまたはguarantee。原契約の年額を期中増額後の表示用年額に流用せず、GM-01C/Dのselectorで変更履歴から導出する。名簿・表示用給与・年次負担を別々の正本にしない。

## 2. 年度枠・留保・確定負担

`annualSpending.js`の計画データはversion/budgetSeason/ledger/authorizations/reservations/resolvedReservations/oneOffCosts。年度許可額と、未充足人数に対する最低維持費を明示する。最低維持費は**すでに給与やオファーで確保した人数を除く不足分**を編成計画から渡す。UIから任意に入力させる値でも、新人の固定人数留保でもない。計算は次のとおり。

`追加余力 = 許可額 − 給与 − 保証残債 − 留保 − 一時費用 − 未充足分の最低維持費`

| 関数 | 責務 |
|---|---|
| quoteAnnualSpendingPlan | 全対象年度の給与/保証/留保/一時費用/最低維持費/余力を分ける |
| assessAnnualSpendingChange | 両球団・全対象年度を同じ条件で審査。金額の書換えや過去費用の削除を拒否 |
| reserveContractProposal | 未確定契約の月割り費用をそのまま留保。条件変更は新IDでreplaceIdを指定 |
| cancelContractReservation | 対象の留保だけ解放。確定済み給与や他の新人留保は返金しない |
| commitContractReservation | 最新の許可額と契約条件を再確認し、契約確定と同じ選手の重複期間に対する競合オファー解放を一つの候補へ適用 |

留保には金額コピーを保存せず、契約proposalから同じ台帳関数で各年の負担を導出する。7/1加入の3年・年俸1億円なら5,000/10,000/10,000万円。受諾前は留保、受諾後は給与となり、本人の追加余力は同じ。競合オファーの解放分は他球団へ戻るが、無関係な新人や期間の重ならない将来契約は維持する。

取消・差し替え・受諾・競合敗退をresolvedReservationsへ保存し、ID・元の条件・解決状態を独立して残す。この履歴には資金を留保しない。解決済みの同条件の提示再送は何も変えず、異なる条件でのID再利用や取消済みの受諾を拒否する。JSON再読込後も同じで、履歴消去や条件の書換えも支出審査で拒否する。閉じた年度の履歴圧縮・退避は、古い返信の期日検査と一緒にGM-01Dで具体化する。

4〜7年目も個別審査し、許可額が未記録なら0や3年予測で補完しない。未知version、未記録金額、安全整数を超える合計、重複IDは例外で停止する。入力自体が正しく資金不足の場合はassessがok:falseと球団/年度別のviolationsを返す。通常収益や賞金を支出許可へ自動加算する経路はない。

一時費用にはコーチ・調査・球場・金銭トレードの金額を明示する。符号付きはtradeだけ。新しい金銭トレードは同じ対象年度で全支払/受取の合計0が必須で、支払側の不足も拒否する。日付・所有権・金額の現実の取引への結び付けはGM-01Cの原子的確定処理で行う。

## 3. 赤字球団と過去の保護

有効な計画の余力は負値を保持する。既存の赤字を隠したり、関係のない球団の赤字で別球団の補強を止めたりしない。

通常の新規支出では、新しい負担を作る球団/年度の余力が負なら拒否する。他球団の競合敗退など、既存の留保解放だけで赤字が改善する行を理由に、資金の足りている勝者の受諾を妨げない。cashless-tradeモードは追加台帳取引が移籍だけで、承認された許可総額/留保/解決履歴/金銭費用/締め年度を変えていないことを要求する。その上で、赤字を含め全対象年度の総負担を悪化させない交換のみ許可する。ゼロ年俸の新規契約を混ぜる、金銭を別記する、7年目だけ悪化させる等の迂回も拒否する。

許可総額は取引中に固定するが、最低維持費は承認額そのものではなく不足人数からの派生値で、欠員補充により減る場合がある。その根拠を実際の名簿から再計算するのはGM-01C。名簿を持たない今回の金額関数だけで、入力された不足人数の正しさを認定しない。

この審査は新しい支出/契約移管の許可用。新しい支出を作らない満了・正式終了や留保取消を、赤字だからという理由で禁止する機能ではない。終了条件そのものの保証・所有権・期間検査は台帳で必ず行う。

台帳の履歴は追加だけを許し、消去・原契約の書換え・閉じた年度へ後から加える変更は拡張と認めない。確定済み一時費用や過去の最低維持費も変更しない。budgetSeasonの切替や新たなオーナー配分は、この新規支出審査で偽装せずGM-01Dの年度境界で処理する。

## 4. 日付と未接続事項

`contractCalendar.js`は#505の厳密な暦日検査を共通化し、既存TRADE_DEADLINE_MONTHを使用する。salary mathはそのまま。試合後の移籍を翌日有効にする日程の解決、現実の所属・育成区分・外国人枠/FA最大3年/最低年俸・CS等の8/31登録スナップショットはGM-01Cの責務。給与の対象期間と登録資格を混同しない。

旧セーブの未知の署名フェーズの推測、旧年度の再計算/返金、保証残債の現行セーブからの復元、公式戦中のコーチ変更、コーチ新料金、オファー配達UI、年度許可額の配布、Workerや委任への新ルール有効化は未実装。履行未確認条項を新制度で新提示しない接続もGM-01C/Dで行う。
