# 戦術試合のCPU編成準備漏れ

作業日: 2026-10-08。開始main: `3e0076fd8148c6d3d5bbb75583e62481da802ceb`。
専用ブランチ: `fix/cpu-game-roster-preparation`、PRのbase: main。

## 範囲と原因

D01のPR #420でCIが戦術第7戦の保存履歴「期待7件/実際6件」で失敗した。traceはCPU対戦の`prepareTeamForGame`で出場不可先発の例外を記録していた。元traceの球団・選手・出場不可となった起点は未特定だが、現行mainには次の処理差がある。

- 通常1試合Workerとバッチは、試合前に既存のCPU編成方針を適用する。
- 戦術試合の他球団処理は古いteamsを直接厳格検証する。CPU編成方針は試合後にしか適用されず、負傷先発がいると結果反映前に停止する。
- 自チームの対戦相手は試合開始時に編成を整備するが、試合終了時には整備前の名簿へ成績を反映していた。昇降格した選手の登録日数等も不一致になる。

これは数値修正D01とは別の進行阻害修正。ユーザーの「続けて」の指示に基づき別PRで扱う。D02〜D06、F3の保存世代、F4全体の再試行・失敗後復旧、保存方式変更、ユーザーの自動編成方針変更、確率・能力・CPU評価の変更は含めない。

## 修正前の回帰

`useSeasonFlow.cpuRoster.test.js`で固定した既存fixtureを使用し、対戦相手と他CPU球団の先発を3日負傷させる。Math.randomを固定し、新規負傷とトレードはテスト内で抑止する。編成管理・厳格検証・成績反映は実コードを使用する。

DHあり/なしとホーム/アウェイの4ケースすべて、修正前に`RosterValidationError`と後処理失敗通知で失敗した。期待値変更や検証回避はしない。

追加した実UI/IndexedDBの戦術E2Eも、未修正mainの別worktreeで失敗。保存後`gameResultsMap`の期待1件に対して0件となり、編成例外と同じ結果未反映経路を検出した。

## 最小修正と保存

- `useSeasonFlow.js`: 開始時に整備した通常の相手名簿を`currentOpp`へ保持し、試合用名簿と区別する。戦術終了時はその名簿へ成績を反映。他CPU球団には通常Workerと同じ既存FULL編成方針を適用してからシムする。ボックススコア・打球アーカイブも実際の相手名簿を使う。
- 新規hook回帰5件: 4境界ケース、成功コールの重複に対する一度だけの反映、日程にないCPU試合を作らないケース。全参加球団の1試合計上、実際の相手登録日数、入力不変、自チーム打順不変も検証。
- `match-history.spec.js`: 既存テストの検証を維持し、CPU負傷編成の実戦術/保存/再開ケースを追加。既存CI smokeはこのファイルを実行するため設定変更不要。

修正途中の実UIテストでは試合用の投手入り打順を通常teamsへ保持する案が保存/ロード時の名簿不一致を起こした。その案を取り下げ、通常名簿と試合用名簿を区別して同じ保存前後一致検証を成功させた。保存の期待値を緩めていない。

saveDataVersion=4、DB構造、保存/ロード実装は変更しない。旧inline v4をロードして現行保存APIで固定編成を設定し、試合後の履歴・全球団名簿・日付・成績が保存/再開後も一致することを確認する。過去セーブの成績や予算の推測補正はしない。
