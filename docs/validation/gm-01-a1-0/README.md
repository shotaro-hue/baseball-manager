## 2. 後続試験の共通ルール

**以下は計画であり、A1-0で合格した試験ではない。** 各IDを後続PRのテスト名/記録へ紐付ける。U=単体、I=実hook/Reducer統合、B=ブラウザE2E、L=長期、P=実iPhone。BはChromiumとWebKitで1worker/retries=0。

- 成功だけでなく、拒否前後の入力参照/JSON/所属/台帳/予算/receiptが変わらないことを確認する。
- 見積→別取引→確定の間で最新状態の再検証を行う。JSONだけでなく本番保存→冷起動→再保存でも冪等性を確認する。
- 期待金額は`monthlyPayroll`の独立した累積差分例から決める。実装の出力をそのまま期待値へコピーしない。
- native契約はFA1〜3年/更改1〜7年。5/7年FAを通す試験ではなく、許可された更改の全期間を試す。
- 制約の適用結果は同じcommandを人/CPU/Workerで比較し、戦略や乱数の選択そのものを同一に強制しない。

## 7. 長期検証の順序と観測

まず**seed=20261030、3年**を固定し、全12球団で接続破綻を修正する。この段階を通過してから**seed=20261030/20261031/20261101、各10年**を同じsource/policyで実行する。seedの変更/追加を失敗隠しに使わない。CPU11球団とユーザー役1球団の操作方針を記録し、ユーザー役にも同じcommandを適用する。

実Appと同じ新CPU・scheduler・年度candidate・save/hydrationを使う。直接teamsを書換える古いharness、`nextClubBudget`でのショートカット、単なる契約APIの反復で3年/10年合格を宣言しない。長期は数値集計、B01/B02は実Appの入口/Worker/描画/冷起動の接続を補完する。

| 進行/年度更新/保存の失敗と復旧 | event単位、失敗注入 | 通常進行の永久停止0、保存失敗後に再試行/正常復旧可能 |
| root/body/chunk/台帳/receipt/backup/使用量/保存時間 | 毎年＋cold reload | 履歴を消して誤魔化さず、基準fixtureの容量上限内で保存・再開。劣化傾向を記録 |
| 旧→新の開始残高 | 移行時と10年後の再照合 | 原証跡保持、偽の過去支払0、不明保証の勝手な確定0 |

容量はIndexedDBが不要になったroot/bodyを回収できることも測る。台帳/receiptの長期増大が問題なら、照合/冪等性を保った別の履歴保管設計を立て、有効化を止める。未検証の切捨てをA1へ混ぜない。

適正な支援額/配分率/成功率は現在未測定。静的最低支援額、旧#503の成績、#515の803回帰等は参照証拠で、新制度の動的合格の代用にはしない。

## 8. リリースの合否

単体/実hook/両browser/旧保存/長期/実iPhoneの必須項目を同一release sourceと選定policyへ紐付ける。各記録は`ID, sourceSHA, policyVersion, seed/fixture, browser/device, command, expected, actual, status, evidence`を持つ。未実施/CI待ち/環境障害は成功に含めない。

A1-1〜4aはゲートOFFなら段階PRとして評価できる。A1-4bは全必須ゲートと不変条件を満たすまでマージ推奨しない。実機/長期が未確認だから期待値を緩める、legacyへ黙って戻す、失敗seedを外すことは禁止する。
