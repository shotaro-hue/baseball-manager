# SAVE-01A — オフライン完全バックアップ・安全な復元 設計

作成日: 2026-10-23  
対象: shotaro-hue/baseball-manager  
確認したmain: 7dc29c0809526ce937e9948b9a0940c7287dc38d（#493マージ後）

## 1. 目的と実際の成功条件

ゲームを10年・20年・それ以上続けても、SafariのWebサイトデータ消去、端末故障、ブラウザ移行、ローカル容量不足から、自分で保管したファイルを使って球団経営を再開できるようにする。

1. **自己完結**: 書き出した1ファイルは元のlocalStorage/IndexedDB、同一端末、元のブラウザプロファイルに依存しない。別端末でも復元できる。
2. **ゲーム内容の忠実性**: 選手/所属/年俸/契約、年度/日付/勝敗、ドラフト/FA/財務、二軍、過去年度・通算・試合結果、メール/ニュース、打球アーカイブの保存済み情報を維持する。
3. **失敗時の保全**: 中断/破損/容量不足/ロック競合/復元ファイル不正では、現存する主セーブ・backup1・backup2・履歴・打球アーカイブを削除・上書きしない。正常復元の直前まで元データで「続きから」が可能。
4. **成功の定義**: ステージ書込・別transaction読戻し・全依存履歴復元・意味検証・冷再読込まで通ったときだけ「復元済み」。ファイルを生成しただけで「iPhoneのファイルに保存済み」と表示しない。
5. **実際に使える**: iPhone Safariの標準ファイル選択/共有/ダウンロードから操作でき、専用PC・クラウドログイン・独自サーバーは不要。

既存ゲーム進行中の未保存変更は、書き出し対象ではない。最後の**正常コミット済み**セーブ時点を明示する。データが失われた後から、消えたIndexedDBを復元することはできないので、事前のファイル保存が必要。

## 3. 形式の比較と決定

| 案 | メリット | 重要な問題 | 判定 |
|---|---|---|---|
| A: 巨大なJSONまたはgzip JSON 1ファイル | 実装が最短 | 20年級の巨大なオブジェクトを一括展開しがちでiPhone Safariのメモリ上限に弱い。部分検証・障害箇所特定が難しい | 非採用 |
| **B: マニフェスト付きZIP 1ファイル** | iPhoneで保存・共有しやすい。複数のDB領域を独立エントリに分割でき、完全性/バージョンを検証できる | ZIPストリーム実装の選定・制限・テストが必要 | **採用** |
| C: JSON等の複数ファイルを個別保存 | 部分書込可能 | iPhoneで一式を持ち歩く/選択する体験が悪く、欠品しやすい | 非採用 |

拡張子は **.bmbackup.zip**、MIMEは application/zip。普通の「全データを書き出す」ボタンとして提供し、ユーザーに内部ストアを選ばせない。ZIPライブラリは実装時に保守性/ライセンス/サイズ/ストリーミングを比較して採用する（特定ライブラリの導入は本設計では未承認）。

**パッケージ規約 v1**:
- manifest.json: formatVersion=1、ゲーム保存バージョン、作成日時、選択した有効ルート世代、各世代の検証状態、ファイルごとの圧縮前バイト数/SHA-256/レコード数、依存性、表示用の球団/年度/日付。
- roots/: 保存候補（主・backup1・backup2）の論理スナップショットと、対応するroot-bodyの本文。破損した復旧世代は除外と理由を明記し、有効な候補の取込みは妨げない。
- chunks/: 有効ルート群から到達可能な seasonHistory/news/mailbox/matchHistory/careerLogs。共有している行は重複格納しない。
- archive/: 打球バッチとメタを小さな分割エントリで格納。集計は再計算して意味一致を検証する。
- 個々のエントリは数MiB程度の**上限付き分割単位**で読み書きし、長いJSON文字列やZIP全体の一括複製を避ける。最大値は実20年相当/iPhone計測後に確定し、年数だけの固定上限は設けない。
- ZIPのCRCだけに依存せずWebCrypto SHA-256で内容を確認する。これは偶発破損対策であり、署名/改ざん防止/暗号化ではない。
- ファイル内容は平文相当で個人のプレイデータを含む。ファイルを外部サーバーへ自動送信しない。自動クラウド同期・パスワード暗号化は今回の対象外。

ファイル名やZIP内部パスはアプリ側で固定生成。復元時には未知のエントリ、重複パス、外部パス指定、圧縮爆弾、過大なエントリ数/膨張率、非対応バージョンを安全に拒否し、未検証の本文を実行・DOMに挿入しない。

## 4. 書き出しプロトコル

1. 画面は**最後に保存できた状態**と保存日時を表示。進行中・dirty・自動保存中は、未保存の変更が含まれないことを明確に示す。安全な状態での手動保存完了後に書き出しを推奨し、失敗した保存を成功に変換しない。
2. 既存の共有saveキューを完了まで待ち、Web Locksの **baseball-manager-save** を用いて保存・削除・復元との競合を防止。現在の主/backup1/backup2を原子的に読み取った論理スナップショットを基準とし、途中で世代が入れ替われば中止する。ロックがないブラウザでは競合安全性を勝手に仮定せずfail-closed。
3. まず有効ルートを通常loaderと同じ復元・意味検証で列挙。主が破損してもbackup1/backup2から回復できる場合はその世代で出力できる。除外世代/最新からの後退を確認画面で表示する。**少なくとも選択ルートの全依存行が揃わなければ出力完了としない**。
4. 保存対象の依存キー閉包を構築。履歴5スコープと旧通算の扱いは保存世代ごとに判定。打球書込queueをflush/retryし、未処理/失敗件数が残る場合は「打球の一部が未保存」と明示して**完全バックアップの成功扱いを禁止**する。
5. 別タブでの打球書込がsaveロック外で動く現行仕様を考慮し、**archiveの読取一貫性の確保方法を実装前に確定**する。推奨はarchiveMutationTailとの直列化窓/明示スナップショット境界と最後の件数・識別子再照合。途中で変化したら中止。snapshot対象の失効を防ぐ間はルートGCを走らせない。
6. 内容ごとのSHA-256を生成しながら、長い同期処理を避けて分割ZIPを作る。ブラウザに戻せる処理単位を設け、メモリピーク/GC/経過時間を計測。完成前にダウンロード/共有を開始しない。
7. ユーザー操作でiOSのファイル保存・共有へ渡す。アプリが確認できるのは**「書き出しファイルを生成・受渡しした」**ことまでであり、「ファイルアプリに保存されました」と断定しない。保存先確認と、別の場所へのコピーを案内する。

書き出しは既存セーブ・バックアップ・参照・metadataを**一切変更しない**読み取り操作。性能/診断ログは任意の独立領域で管理してもよいが、保存本文・選手情報・ID・ファイル本文をconsole診断へ出さない。

## 5. 復元プロトコル（最大の安全要件）

**「読込プレビュー → ユーザー明示確認 → 隔離領域へ仮投入 → 完全再読込検証 → 現行参照の最終切替」**とし、ファイル選択の時点で既存セーブを書き換えない。

1. title画面のinput[type=file]でローカルZIPを選択。manifest/schema/entry count/サイズ/各SHA-256/ZIP構造/依存閉包を検査。許可された形式以外はすべて拒否。成功後にプレビュー（球団、年度、日付、元世代、打球記録の有無、既存セーブとの比較）を出す。
2. 既存セーブがある場合は「現在のセーブが切り替わる」「復元前のセーブも保護する」を説明し、**別の明示操作で確定**。ゲーム稼働中の未保存変更は勝手に捨てない。初版の入口はタイトル画面のみ。
3. saveキュー・削除処理を排他し、ロック取得時にルート観測値・削除epochを再確認。ファイル読込中の別タブ書込があれば**自動上書きせず競合中止**。
4. 復元元のsaveIdが現行データと同一でも衝突しないよう、**新しいsaveId**と新しいgeneration/root-bodyキーでIndexedDBに**不変ステージ**を作る。manifest内の全参照・行のsaveId・キー・署名を整合的に再生成。既存の主/backup1/backup2へは一切書き込まない。
5. 打球batch.idは現行 **saveId:year:gameId:playerId** 形式で新IDへ再採番し、aggregatesは **createBattedBallAggregateId** と既存の再構築関数で作る。archive metaも新saveIdへ写し、再構築前後のeventCount/集計値を照合。これによって現存セーブと同じ旧saveIdのアーカイブを書き潰さない。
6. 完了済みIndexedDB transactionとは**別のtransaction**でステージを再読込。標準loader相当の全スコープhydrate・二軍/契約/財務/チーム意味検証に通す。出力元からsaveId/新世代キーだけ除いたプレイデータのSHA-256と再構築された打球イベント/集計が一致することを確認。検証コードは既存のsave検証処理を共用するが、**loadGame()等の副作用を持つ本番公開処理は使わない**。
7. 最終参照切替の前に、現在の有効primaryを**復元前リカバリ参照**として専用小キーに保護する。このキーはsave_chunksのGC保護対象・削除/回復の判定対象に追加し、旧世代を次回保存で誤収集しない。旧primaryが破損なら有効なbackup候補を優先する。
8. すべての検証に通った時だけ、小さいlocalStorageの**primaryルート参照を単一setItemで公開**。既存backup1/backup2を復元前に破壊しない。対応するmetadata/内部cache/世代観測/復元前参照を整合化。公開後の新規タブ cold reload でも同じ内容を検証してはじめて完了とする。
9. 公開後に検証エラーが起きたら、復元前参照からの**明示復帰**を可能にする。自動的に旧履歴をGCしてはならない。旧参照保護の解除・期限・旧archiveの整理は「復元後のセーブ成功確認 + 明示確認」から独立の保守処理にする。
10. 途中失敗では現存3ルートの文字列/世代・参照中IndexedDBデータ・打球ID行がバイト一致することをテストで証明。孤立ステージを次回の安全な保守で回収してよいが、失敗したrestoreが残すデータで本来の保存をquota不能にしてはならない。

**重要**: 現在の **collectUnusedChunks()** は主・bk1・bk2をGCの保護根としている。新しい復元前参照を考慮せずに投入すると、次のsaveでロールバック不能になる。この設計と検証は必須。現行 **deleteSave()** の副作用/epoch、別タブの観測値、battedBallArchiveの非同期削除も一体で検証する。

## 6. UI/操作とユーザーへの表示

- タイトルの既存セーブカードに「バックアップを書き出す」を追加。セーブが読めない場合も有効なバックアップ世代からの書き出しへ誘導。
- セーブが無いタイトル画面にも「バックアップから復元」を常時表示。削除/新規ゲーム操作とは独立。
- フォルダを指定する特殊APIは要求しない。iPhone Safariは共有/ダウンロードと標準ファイル選択を使う。端末で保存先を確認してもらう。既存データを消す手順は勧めない。
- プレビューで **既存 → 復元後** の球団/年度/試合/保存日時、ファイル容量/検証結果、選択中の復旧世代を比較する。明示的な「復元する」と「キャンセル」を設ける。
- 進捗: 読込、完全性検査、仮投入、検証、参照切替、完了。エラーはコード付きで再試行可否を区別し、機密本文/stack/ファイル名/選手情報を自動ログ送信しない。
- 390px画面、VoiceOver/キーボード、フォーカス復帰、処理中連打、ファイルピッカーのキャンセル、バックグラウンド移行/端末スリープでも古い画面状態を勝手に「成功」としない。
- 「Safariからホーム画面に追加」は独立ストレージになる場合があるため、同じセーブが自動で見えると案内しない。外部ファイルによる移行を優先する。

## 7. 補助策：永続化と容量診断

WebKitは容量上限だけでなくWebサイトデータの自動削除・サイトデータ消去の可能性がある。Safari17以降の **navigator.storage.persisted()/persist()** を、サポート状況に応じて状態表示/任意申請できるか調べる価値がある。ただしWebKitの判定・ユーザー操作・端末状態に左右され、**外部ファイルの代わりにはならない**。

公式資料:
- https://webkit.org/blog/14403/updates-to-storage-policy/
- https://webkit.org/blog/14445/webkit-features-in-safari-17-0/
- https://webkit.org/tracking-prevention/

永続化APIを追加する場合も、権限未付与/拒否/未対応でセーブ・書き出し・読込を妨げない。新規バックアップ機能と混ぜてP0原因判定を曖昧にしない。

## 8. RED→GREEN・総合QAの受入条件

### 内容の完全性
- 初期2026年、2026年8月1日106戦目、年度末、オフシーズン編成、legacy v3/v4/v5/v6、主破損→bk1/bk2正常、3世代異なる年度/保存時点。各有効ルートを失わない。
- 20年**相当の容量fixture** と実際に複数seedで**ゲーム進行した年次fixture**を区別。完走年数は計測して記載し、未実施を実施としない。
- 冷起動/別ブラウザプロファイルで、球団/選手ID/契約/年俸/一軍二軍/成績/通算/年度/FA/ドラフト/財務/メール/ニュース/ボックススコア/打球イベント・集計を比較。運搬時にIDが再採番されるsaveIdは意味比較から除外、プレイヤーID等は保持。

### 破損と失敗の試験（成功扱い禁止）
- ZIP manifest/entriesの欠品、重複、順序変化、未知形式/将来schema、SHA不一致、ZIP CRC破損、展開サイズ偽装・高圧縮率、文字列/JSON破損、打球batch一部欠落。
- userキャンセル、ブラウザダウンロード拒否、WebLocks取得不可/別タブ保存、エクスポート中にroot更新、queue未完了、打球書込失敗。
- import時の各IndexedDB transaction abort/quota、読戻し本文不一致、意味検証失敗、primary公開時localStorage quota、公開直後の画面中断/タブ強制終了。
- **失敗前後**で既存primary/bk1/bk2/履歴/打球/メタが一致し、タイトルの「続きから」が可能。成功後の新セーブ検証と旧セーブへの手動復帰も両方通す。
- ステージ孤立行の安全な後片付け、GCが復元前参照を守ること、復元後のsave・backupローテーション・deleteとの組合せも確認。

### 実行環境・性能
- Vitest（実IndexedDBに近いfake-indexeddb）とChromium / mobile WebKit、幅360/390/1440、単一worker/retry0、既存保存/削除/別タブ/キャリア/二軍/打球/オフシーズンの回帰を維持。
- 10年/20年相当のZIPサイズ、エントリ数、最大一時メモリ、メインスレッド停止時間、作成/復元時間を**前後・実測**。数値閾値を根拠なく緩めない。20年相当をiPhone実機で扱えない場合は未合格・分割改善する。
- **実iPhone Safariで書き出し→「ファイル」保存→Safariのサイトデータが無い別プロファイル/環境でファイルを選択→復元→再読込→数試合進行→再保存**を必須受入。ユーザーの現存データを使う破壊試験は行わず、試験プロファイルで検証する。
- #493の未完了事項である実セーブの保存成功/再読込確認は別の受入であり、本設計だけで解決認定しない。

## 10. 実装開始前に解決する技術上の判断

1. **打球アーカイブ整合性**: saveロックとarchiveMutationTailが別系統。export/import/通常更新をどうシリアライズするかを先に設計・REDテストする。
2. **ZIPストリーミング**: iOS Safariで数十～数百MiB規模を巨大Blobにせず扱える実装を検証する。ライブラリが全展開前提なら不採用。必要なら内部形式を再検討するが、外部1ファイル条件は維持する。
3. **GCと復元前保護**: cleanupSaveChunks/collectUnusedChunksとdeleteSaveの双方が専用保護参照を理解するようにする。既存ロールバック検証を先行REDで追加。
4. **旧形式移行**: v3–v5のcareer_logs、v5/v6の異なるscopeとlegacy root圧縮を、正常な本番ロード手順に沿ってバージョン別に再構築する。

設計の承認条件は「欠落し得る保存領域がない」「公開前失敗で既存3ルートを変えない」「外部1ファイルから元環境無しに再開できる」「iPhoneで利用できる現実的メモリ」の4項目である。
