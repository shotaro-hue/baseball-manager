# UI-01D: まとめシム結果

基準main: `fade70dd427f46638e9474c6fab462f1fe87bedc`（#461マージ）。
UI-01Dは今回のまとめ結果移行の分割名。日程・球団詳細の試合履歴全体は含まない。

## 目的・範囲

スマホの「編成→まとめシム→結果確認→編成見直し」を仕上げる。
DES-01のネイビー要約帯、白い一覧、青の操作色と既存Button/StateLabel/Sectionを使用。
専用batch-result.cssをスコープし、他画面の旧CSSは維持する。

- 期間戦績・順位変化を上部へ。現在一軍の疲労／負傷と期間内負傷を区別。
- 初期8試合・8件ずつの追加表示・遅延ハイライトを維持。
- 記録不足を引き分け／本塁打0へ補完しない。ログ記録あり試合数を明記。
- 詳細記録なしは無効操作と理由。Routeで実gameResultsMapを確認する。
- 詳細から戻る際の表示件数をgameResult内の一時的UI情報として保持し、同じ試合へフォーカス復帰。
  batchResults参照の一致で同じ結果への復帰を判定し、新しいまとめシムには持ち越さない。
  永続state／保存形式の追加なし。非同期ハイライト完了で再度フォーカスを奪わない。
- 保存待ち／保存中／成功／失敗・部分履歴失敗は既存gs実状態を表示。
  結果集計完了を保存成功にしない。保存／再試行は既存ホームへ戻る。
- 集計例外を表示し、結果一覧・戻る操作を維持する。

非対象: シミュレーション・成績集計・Worker・保存・ナビ・新規試合進行・日程／球団詳細画面。
開幕戦相手AVGは独立PR #462で修正し、本ブランチのResultScreenへ混在させない。

## 検証経路

- unit `batchResultDesign.test.js`: 新規9件が修正前に失敗→修正後成功。
  レビューで見つかった別バッチへの表示件数持越し・読み上げ名の情報不足も2件RED→GREEN。
  既存batchResult/mobileFlowと合わせて21件成功。
- 新規 `batch-results.spec.js`: 7幅（360/390/760/761/1023/1024/1440）×10表示状態、
  keyboard、44px操作、横はみ出し、欠測／無効／集計エラー、追加表示。
- 実App 360/390/1440: 10試合進行→追加表示→最後の試合詳細→同じ行にフォーカス復帰
  →編成一覧→保存→ロード。結果map・teams一致、gameDay=11。
  390pxはさらに次の10試合を進め、初期8件へリセットとgameDay=21を確認。
  20日目で発生し得る既存記者会見は実UIで回答してから保存する（イベントを無効化しない）。
- 完全な初回成功実行は10 E2E成功（約1分）。レビュー後の差分は関連ケース再実行とPR CIで確認。
  最終390pxの繰り返し進行・記者会見回答・保存再開は1成功（約27秒）。
- 初回ブラウザ試験はエラーfixtureが例外を発生させない設定と、既存編成の見出し指定誤りで失敗。
  fixture／selectorを修正し、期待するエラー・遷移検証は維持。skip・timeout延長なし。
- 新規specは通常CIのinitialization-and-progressionへ追加。#462のmatch-history行とは独立。
  全unit/build/中核E2Eの結果はPRの同一SHA CIへ記録する。

未検証: iPhone実機、Safari/WebKitのこの画面、スクリーンリーダー、実複数年バランス、全E2E。
