# 保存容量不足の緊急修正設計

基準main: `756af98dafb219f9e4d3f540c69148be38cb389f` (#490/#491マージ後)。全1843 blobをGitHub treeと照合済み。

## 目的・受入条件

既存セーブを保全し、2026年実サイズおよび10年・20年相当の履歴を保存・復元できること。保存中断・容量不足・破損・別タブ競合で前回の正常セーブを失わないこと。成功は書込完了と読み戻し検証後に返す。実iPhoneは未検証とする。

## 調査と選択

履歴5scopeはIndexedDBの不変世代に分離済み。本体は選手・二軍台帳等を含むLZ圧縮文字列のままlocalStorageに主・backup1・backup2を置く。既存2026 fixtureは年度末teamsだけでJSON約14.3MB。端末空き容量とlocalStorage上限は別問題。

1. **採用: 大きい本体をIndexedDBへ不変コピー、localStorageは小さい参照。** 既存世代・排他・原子的root差替を活かす。履歴や選手情報を切り捨てない。
2. 本体をさらにフィールド単位で分割: 更新効率は良いが全stateの網羅と互換性に影響が広い。本緊急修正では見送る。
3. バックアップ削減や履歴切捨て: 復旧性・目的を損ねるため採用しない。

## 保存プロトコル

- 64KiBを超える圧縮済本体は既存save_chunks内の`root-body:`不変行へ保存する。小さな既存形式は継続読込・保存可能。
- root参照はversion/key/signatureのみ。本文・ID・選手名を含めない。署名は偶発破損検知用で認証ではない。
- IndexedDB transaction complete → 別transactionで本文の一致と署名を検証 → 通常のhydrate/validationで全依存世代を読み戻す → localStorage.setItemで参照を原子的に公開。
- 公開前に中断した場合は既存root/backupを一切変更しない。孤立行は後続の保守で回収可能。
- ローテーション対象の旧本体も同じ検証を通して参照化してからコピーする。従来rootは新しい参照の公開完了まで残す。既存セーブ削除・初期化・読み込みだけの自動書換はしない。
- root参照行と既存履歴世代のGCは、主・backup1・backup2すべての参照を保護する。解釈不能なrootがあれば回収を中止する。
- 既存Web Locks、観測値比較、削除epoch、読込epochを維持する。別タブで古いコードを実行している場合の混在更新はサポートせず、全タブの更新を実機手順に含める。

## 診断と限界

画面の診断コピーは固定の数値・列挙値のみ。容量内訳はlocalStorageの全キー総量、主/各backup、IndexedDB store別JSON概算、StorageManager見積もりを区別する。本文・キー・ID・例外メッセージ/stack・URLをコピーしない。Clipboard API失敗時は選択可能なtextareaを提供。

ブラウザ全体の容量不足・サイトデータ削除・OS強制終了時の物理ディスク耐久性は完全保証できない。10/20年相当は実シーズン履歴を拡張した容量試験であり20年間の全ゲームロジック検証とは区別する。
