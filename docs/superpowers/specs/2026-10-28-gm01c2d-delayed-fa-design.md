# GM-01C-2D 同一年度のFA後日回答

基準main: `daddaf8a17f14e533ce290e1ec20ec0d74640779`（#510マージ済み）。親設計: [GM-01 第6節](./2026-10-26-club-management-gameplay-design.md)。工程ごとに実装・検証・独立PR作成まで進める既存の承認と、今回の継続指示に基づく。

## 目的と受入条件

共通FA取引は現在、提示日と受諾日が同じ場合だけ成立する。後日の回答を接続する前提として、提示時の条件を保全しながら、受諾日以後の実給与負担、名簿、競合留保、確定履歴を一つの候補stateで更新する。

- 既存の`offer-fa` / `accept-fa` / `cancel-fa`を継続する。受諾日は信頼済みstateの`date`を使い、コマンドからの任意日付を受け付けない。
- 対象は同一年度の開幕前・シーズン中。開幕前の提示を同年度シーズン中に受諾できる。シーズン中の提示を開幕前へ戻して受諾すること、提示日前の受諾、翌年度・オフへの持越し、7月31日後の新規獲得は拒否する。
- 提示の年俸・年数・契約ID・選手ID・球団・保証・署名年度・合意フェーズ・満了年度・区分は変えない。受諾時の契約効力日だけを後ろへ進め、過去の給与を発生させない。初年度の2〜11月月割りを既存台帳で再計算し、将来年度は元の契約年額を維持する。
- `commitContractReservation(plan, proposal, { effectiveDate })`を限定拡張する。後日効力を指定できるのは`kind=offer`・新規獲得だけ。更改と新人の効力日を変更しない。元の留保は`resolvedReservations[].proposal`へ残し、後日受諾だけ任意の`acceptedProposal`へ実際のsign条件を記録する。同日受諾の既存データ形は維持する。
- 引用・審査・JSON再読込では、`acceptedProposal`が元のFA条件から効力日だけ後進したものか、台帳のsignと完全一致するかを検証する。元の提示・実受諾・解決履歴の消去や書換えは拒否する。元の提示と同じIDの再適用は一度だけ、別IDでの二重受諾は拒否する。
- 見積後に予算・市場所属・引退・育成区分・受諾済み新人を含む70人枠・配置制限が変わっても、最新stateで再審査する。受諾で競合留保を解放し、別件の更改・新人・FA留保と既存費用は維持する。赤字の敗者・取消を新規支出扱いしない。
- 登録期限後でも当年度内の取消は可能。日付経過だけで自動受諾・自動取消はしない。見積と失敗は全体非変更、旧`budget`は更新しない。

## 方針と代替案

| 方針 | 判断 |
|---|---|
| 提示日に遡って契約する | 不採用。未加入期間の給与と所属を発生させる |
| 留保の提示日を上書きする | 不採用。提示と受諾の履歴が失われ、既存の識別情報保護にも反する |
| **元提示を保全し、同じ解決履歴に後日受諾条件を付記する** | 採用。既存台帳・審査・競合解決を再利用し、名簿・支出を一度に確定する |

この小PRへの分割と任意フィールド/APIの命名は実装担当の判断。既存JavaScript/Vitestを使用し、依存・CIは変更しない。提示時の合意フェーズを保持するため、開幕前からシーズン中に進んでも満了年度を再導出しない。

## 非対象と後続

オフFAの翌年効力・加入、本番hook/CPU/委任/Workerへの接続、実際の年度更新・旧保存移行、UI/コーチ、係数校正、実iPhone性能は後続C-2/D。今回は新制度state上の同一年度FA後日回答であり、新制度を本番有効化しない。新しい回答期限・評価式・乱数・自動失効方針は導入しない。完全バックアップ/復元は保留。main直接push・マージ・自動マージは行わない。
