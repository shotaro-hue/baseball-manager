# FIX-T：トレード成立時の整合性

基準main: `686af127920b78e0c108f92a42eb5a835d90dfee`（DOC-01反映）。対象は青写真のBUG-T01/T02/T03。UIテーマ、セーブスキーマ、ドラフト、二軍成績は対象外。

## 原因と修正

- 手動入力は万円なのに `handleTrade` が×10000して予算を控除していた。500万円の入力が5,000,000万円の控除になった。CPUメールの円→万円換算も直後に再乗算されていた。
- `evalTradeForCpu` も円想定の除数を万円入力に使用していた。既存の評価係数に相当する万円換算（/10）へ修正。評価モード・承認閾値の再設計ではない。
- 相手が追加で欲しい選手を相手の選手一覧から選び、自球団の獲得側に追加していた。自球団の未提示選手から選び、放出側へ追加する。選手要求と金銭要求は一つの分岐で生成し、表示されない金銭を同時に請求しない。
- 手動・CPUオファー・メールは共通の `applyTradeTransaction` へ渡す。CPU間取引も同じ検証を経た後、既存の自動編成と `validateTeamRoster` を使う。

## 取引の契約

内部金額は万円、正は自球団から相手への支払い、負は相手から受け取る金額。**既存のCPUオファー/メールのcashは円のまま維持し、受諾境界で一度だけ換算する。** 古いメールを含むセーブスキーマを変更しない。

所属は最新の一軍＋二軍とIDで確認し、古いオファーの選手オブジェクトを状態へ戻さない。ID 0は有効。ID未記録、同一球団取引、重複選択、別所属、重複所属、無効金額、予算不足、両球団の支配下登録枠超過は成立前に拒否する。入力の球団・選手を直接変更せず、両球団の新状態をまとめて作る。

一軍満員・育成・負傷・登録待ち・外国人制約にかかる獲得選手は二軍へ置く。放出者は両球団の一軍/二軍・DH別打順・守備指定・ローテ・継投指定から除去する。手動操作では他の編成選択を全面自動化しない。編成の不足は試合開始側の既存検証で扱う。CPU間取引の既存自動編成は維持する。

成立はbooleanで返し、成功時だけ履歴・ニュース・取引ログ・解決済みメール・成立画面を更新する。同一イベント中の連続確定は反映待ちとして拒否し、再描画後も所属変化で再実行を拒否する。保存・再開後の解決済みメールは再実行しない。期限は既存の `gameDayToDate` と `TRADE_DEADLINE_MONTH` に従い実行直前に再確認する。
