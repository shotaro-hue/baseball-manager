# ゲームロジック監査（2026-10-07）

試合後更新の差への対応を [試合後処理の統一](postgame-flow-consistency.md) に記載した。以下の根拠・診断値は監査時点の記録。FA登録日数と収入の経路差は共通処理で修正し、収入の開催地別ルール・財務表示との整合性は別課題として残す。

対象はmain `0c0f13ba470be1ef5d40d30caac7eadb2c6b3b3f`（PR404・408取り込み済み）。目的は一律の削除ではなく、ユーザーの判断に対応する効果が実装されているか、操作経路を変えても同じルールが適用されるかを確認すること。

試合・戦術・まとめてシム、試合後更新、編成・昇降格、FA・通常契約・更改、スカウト・ドラフト・育成・コーチ、引退・ポスティング、財務・人気・オーナー信頼、順位・プレーオフ・表彰、年度更新・保存、物理演算と検証スクリプトの主要入口を確認した。exportの参照検索だけで不要と判断せず、内部呼び出し・Worker・動的import・テスト・旧セーブの用途も確認した。全分岐・全旧セーブを網羅した監査ではない。

今回修正するのは複数年検証の対象・年度更新・市場の旧所属・比較判定。以下のゲーム本体の課題は未修正で、既存機能の入口やセーブ項目を削除していない。

## 優先度と証拠

P1は結果・権利・所属・経済へ影響する整合性問題、P2は効果未接続・状態や表示の不整合、P3は互換性を確認したうえで整理する候補。「再現」は固定条件の診断実行、「コード確認」は呼び出しと更新箇所を確認、「判断が必要」はルールの変更が必要な項目を示す。

## 再現の記録

4球団をseed 321で生成・開始編成を最適化。`quickSimGame` は1–0／ログ空、負傷生成は空に固定し、4月1日の対戦を0対1・2対3に設定した。同一snapshotをSingleDayとBatch（1日）へ渡した診断値。物理乱数差による結果ではなく、試合後更新の差を切り分けた。

同じ生成球団とFA候補を使い、一軍28人ではCPU獲得0、一軍27人では1。ユーザーの配置判定は一軍28人でも「登録枠が満員」の二軍配属だった。予算・要求額を変えず、枠条件だけを切り替えた。

同じ3年・同額のオファーで、インセンティブなしの評価66に対し、出来高30%・タイトル3,000万円・オプトアウト付きは75。精算実装の欠落はソース参照調査で確認し、この実行が契約成立・実際の支払いまで再現したとは扱わない。

200打席200打数・安打／四球／長打0の野手の成績評価は50（中立）。ID 0で同じ選手を格納しても `resolvePlayerById` はnullだった。調査用の一時的診断テストは4件成功。既存不具合を正しい挙動として固定するためのテストには含めない。

## 不要と判断していないもの

- `hrMod`・`hitMod`、`applyStadiumFactor`、`adjustResultByPhysics` は現行試合には効かないが、互換exportや旧検証の参照がある。削除は参照先の移行と一緒に行う。BalanceTabの現行EV・LA・三振・四球などの補正は実際に使用されている。
- `ownerTrust` はPlayoffRouteで変化し年度予算に作用する。フォームは試合後に更新され打撃と起用評価へ、育成目標は `trainingFocus` を経由して成長へ接続する。名前だけで形骸化と判断しない。
- 人気は試合・会見・オフシーズンで更新され収入へ、コーチは成長・走塁・疲労／回復などへ接続する。継続給与が未接続でも効果そのものは無効ではない。
- IndexedDBの履歴・打球アーカイブ、保存キュー、旧セーブ移行は普段の画面から見えなくてもデータ保持・復帰のために必要。
- `calcBallDist`、`lookupBallDist`、`seriesWinner`、`calcCpuBatterEvaluation`、一部性能ログAPIは本体から直接使われない候補。補助スクリプト・テストや内部利用があるものを混ぜて一括削除しない。使われないexportを残す費用より上の不整合を先に直す。
