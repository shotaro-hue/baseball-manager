# レギュラーシーズンの試合後処理の統一

対象は main `7b4e1bf66f5ab4e30926849dd6a357a8fdf79366`（PR409取り込み済み）の監査で見つかった試合経路の差。

通常試合・戦術試合・SingleDay Worker・Batch Workerの全参加球団に、`regularGameUpdates.applyRegularSeasonTeamUpdate` を適用する。成績・疲労・負傷回復・守備位置練習・一軍登録日数・登録クールダウン・負傷判定／履歴・勝敗／得失点・ローテーション・人気・収入を同じ順序で処理する。二軍は負傷回復と登録クールダウンを進める。

結果ログの自軍／相手の視点と実際のホーム／アウェイを分け、ビジターでの投手疲労も実際の守備イニングで算出する。負傷通知、保存済み結果、ボックススコア、打球アーカイブ、ユーザーとCPUの編成自動化の入口を保持する。

一軍登録日数は従来どおり参加したゲーム日ごとに1日加算する。暦日や休養日への変更、過去セーブの未加算分の推定補完は行わない。新しい負傷は既存負傷の回復後に登録するため、発生当日に残日数を消費しない。

収入は現行の「試合に参加した双方へ加算」というルールに揃える。対戦相手への欠落を修正するため、従来と比べCPUの登録日数・収入が増える経路がある。チケット／スポンサー／グッズを本拠地開催・年間・毎試合のどこに割り当てるか、財務UIの71〜72試合見込みとの整合性は引き続き別課題。要求年俸・FA宣言率・物理演算・投手交代の係数は変更しない。

通常・戦術のCPU間トレードは、試合後の球団状態を使う。以前はトレード成立時に試合前の配列で全球団を上書きし、当日の更新が失われ得た。全試合の更新・CPU編成・トレードを反映してから球団状態を保存し、オールスター選出にも更新後の状態を渡す。

検証は4経路×ホーム／アウェイ×勝利／引分の同条件比較、登録日数・収入・ローテ・二軍回復・練習・クールダウン・入力状態の不変性、ビジター投手疲労、ID 0の新規負傷、通常／戦術のトレード成立時の更新保持。比較テストでは編成選択と負傷発生の乱数を固定して試合後ルールを切り分け、実際の編成・CPUトレードは既存テストでも検証する。

スマホ目視とブラウザE2Eは未実施。監査で残った通常契約の迂回、CPUのFA配置、プレーオフ引分、スカウト、契約インセンティブなどはこの変更の対象外。Sitesには変更を加えない。

検証結果：全体テスト479件成功・既存2件スキップ、本番ビルド成功。大きいチャンクの警告は既存。テスト生成物 `scripts/physics-hr-report.json` と `node_modules` はコミット対象外。
