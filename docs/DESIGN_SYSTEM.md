本書は将来のUI/UX方針の正本。最終デザインとしてのCalm Dugout方針を終了し、**スポーツ分析ハイブリッド**へ移行する。放送系スポーツデータの緊張感と、業務分析ツールの可読性を両立し、「状態把握 → 根拠を見る → 判断・実行 → 結果 → 振り返り」をスマホで一貫させる。

具体的な配色・書体・余白・トークン・ナビ・全画面構成はDES-01で代表モック承認後に確定する。既存Calm系の配色・部品を新規画面のデザイン規範として再採用しない。**旧CSSと既存UIは、該当範囲の置換・検証が完了するまで維持する。** 既存画面の小修正では現在の見た目との整合を保ち、新方針だけを根拠に全面改修しない。

[全体改革の青写真 v1](./REFORM_BLUEPRINT_V1.md) は一次監査・年間フロー・改善ロードマップの参照元。同書の「最新mainとの照合」注記を含めて読む。疑義・理想案を現行仕様や実装済み機能と混同しない。本書と青写真の具体案が異なる場合、現行の開発基準は本書、ゲームの振る舞いはSPECと現行コード・テストを照合し、未確定事項はモック承認へ戻す。

DOC-01は文書のみを変更する。ゲームロジック・UI・保存形式・CSS・テスト設定は変更しない。ブラウザ表示・実機操作・保存挙動の新規検証は行っておらず、全画面が基準を満たすという認定ではない。

## 1. 目的と適用範囲

目的は、スマホで「編成 → 試合進行 → 結果確認 → 編成見直し」を迷わず行えること。広告LPのような見栄えや装飾量ではなく、判断に必要な情報と操作が見つかることを優先する。

- 開発・検証・PRの共通ルールは [AGENTS.md](../AGENTS.md)、ゲームの振る舞いは [SPEC.md](../SPEC.md) を参照する。本書はゲーム仕様を上書きしない。
- 今回の明示的な依頼と合意済みスコープを守る。本書との差異は理由を記録し、未依頼の改修へ広げない。すでに合意した小修正で再承認や複数案を必須にしない。
- [旧UI要件書](./baseball_manager_ui_requirements.md)、[旧ナビ提案](./BOTTOM_NAV_REDESIGN.md)、[design-qa.md](../design-qa.md) は履歴資料。過去の「次に実装する」「未完了」「合格」を現在の指示・状態として使わない。
- 新規画面を毎回別テーマにしない。既存部品と画面固有の例外を確認し、変更対象だけ段階的に揃える。文書整備と、全体のトークン化・CSS再編・画面改修は別の変更として扱う。

### 実装上の注意

Calm系CSSと旧CSS、インライン指定、`!important` が併存している。セレクタ・読込順・適用スコープを調べずに末尾へ上書きを追加すると、他画面へ影響する可能性がある。既存変数が効くスコープなら再利用し、ない場合は対象クラスへ限定する。架空の共通トークンや汎用コンポーネントが実装済みだと仮定しない。

`useResultDialog` のフォーカス対象は現状 `button`、`select`、`[tabindex="0"]` に限定される。入力欄・リンク・入れ子ダイアログ等を追加するときは、そのままで十分とはみなさず、関連実装とテストを確認する。

## 3. 画面で最初に判断できること

| 画面 | 優先する判断・操作 | 詳細側へ置くもの |
|---|---|---|
| ホーム | 現在の戦績、次の対戦、進行可否、要対応事項から次の行動を選ぶ | 長期推移、全指標、細かい進行設定 |
| 編成 | 起用選手・打順・役割・状態を比較して変更する | 全能力、通算成績、詳細な育成設定 |
| 日程・結果 | 対戦と結果を探し、該当試合を開く | 詳細ボックススコア、過去年度、カレンダー |
| 成績・選手詳細 | 同じ条件の数値を比較し、起用判断につなげる | 指標の説明、算出条件、細分化した分析 |
| 契約・FA等 | 対象・条件・費用・期限・取り消し可否を確認する | 交渉履歴、補足ルール、詳細内訳 |

これは優先順位の基準であり、新機能の追加指示ではない。未実装の情報は作り足さず、表示可能な実データと既存の処理を確認する。

## 4. 色・文字・余白

### 配色（旧Calm実装の参照値。新デザインの指定ではない）

| 用途 | 参照値 | 再利用時の注意 |
|---|---|---|
| 基本面・主要文字 | `#fff` / `#17243a` | `.calm-detail` では `--detail-surface` / `--detail-text` |
| 補助文字 | `#53657c` | `--detail-muted`。薄くしすぎて読めなくしない |
| 主操作・リンク | `#1262d4` / `#095cc7` | 主ボタンは `.calm-primary`、リンク色は `--detail-blue`。別用途の青を機械的に統一しない |
| 淡青の補助面・罫線 | `#edf4fc`、`#f0f7ff` / `#dce6f2` | 状態や領域の区切りに限定。すべての情報を色付き箱にしない |
| 成功・警告・危険 | `#14714b` / `#805700` / `#b42332` | `--detail-good` / `--detail-warn` / `--detail-bad`。文字ラベルも併記 |
| フォーカス | `#377ccc`、3pxのoutline | 既存の `:focus-visible` を参照。輪郭が切れないことも確認 |

この表は既存画面を保守するための履歴情報であり、新配色の承認ではない。新UIの配色はモックで検討し、承認後に本書へ記録する。

これらの `--detail-*` は `.calm-detail` 内の変数であり、全画面の `:root` にあるわけではない。CSSの実値はソースを正とし、色やトークンを変更するPRでは本書も更新する。球団色は識別の補助に使い、主要操作や警告の意味を球団ごとに変えない。

### 移行期間の可読性基準とDES-01への候補

- 以下の書体・寸法は移行前の保守目安。新UIの具体的な書体・余白・角丸等のトークンはモック承認前の候補として扱い、可読性・操作領域の条件を満たす組合せをDES-01で確定する。
- 日本語本文は既存の `Noto Sans JP` とフォールバックを基本にする。「AIっぽさを消す」ためだけにフォントやライブラリを増やさない。旧画面の表示用フォントは対象外まで一括変更しない。
- 本文・主要操作は16pxを基本、一覧・表は14pxを基本とする。補足は12〜14pxに留め、主要な判断材料を9〜11pxへ縮めて収めない。見出しは画面24〜28px、節18〜19pxを目安にし、既存PC画面の例外は役割で判断する。
- 本文の行高は1.6前後。数値比較は桁・単位・小数点の位置を揃える。`font-variant-numeric: tabular-nums` は採用候補であり、全画面への適用済み設定ではない。
- スマホの左右余白は16pxを基本とし、関連要素の間は8〜12px、領域内は12〜16px、節間は24pxを目安にする。これは配置の基準であり、旧 `--sp-*` を全置換する指示ではない。
- 角丸は通常4〜8pxを目安とし、影は重なりやダイアログ等を示す用途に限定する。カード全面禁止にはしない。対戦情報や独立した操作領域のまとまりには使える。
- 文字と背景、操作部品と背景のコントラストを実際の組合せで確認する。勝敗・警告・選択状態を色だけで表現しない。

## 5. レイアウトと情報密度

| 避けるもの | 代わりに行うこと |
|---|---|
| 指標ごとの同じカード、カードの入れ子、巨大な余白 | 比較は行・列を揃えた表やリスト。独立した意味のまとまりだけ囲う |
| 管理画面の巨大なヒーロー、意味のないグラデーション・影 | 通常サイズの画面見出し、区切り線、必要な主操作の強調 |
| 見出しと同じ説明文、すべてのラベルへのアイコン | 判断に必要な説明だけ残し、既存のPhosphorアイコンは操作・識別の補助に使う |
| 同じ強さのボタンを並べる、主操作を複数箇所に反復 | 各操作領域で主操作を明確にし、補助操作はリンクや副ボタンにする |

「概要を先に、詳細は展開」を基本とするが、比較に必要な項目まで折り畳まない。展開・タブ・フィルタの状態は見分けられるようにし、詳細を閉じた後も対象や位置を見失わせない。

ページ全体の横スクロールは発生させない。横長の表・カレンダーは専用領域の中でスクロールさせる。スマホでは下部ナビ・比較トレイ・固定ボタン・safe areaによって最終行や操作が隠れないことを確認する。PCは比較の一覧性を増やし、モバイルの一列をそのまま引き伸ばさない。

## 6. 表と数値の意味を守る

- 対象選手・球団の名前列と見出しを追えるようにする。固定列が「第1列」とは限らない。現行の打順表・順位表の例外を確認し、固定列同士の重なりを検証する。
- 長い日本語名でも識別できるよう、折り返し・列幅・詳細導線を選ぶ。省略する場合はタップや詳細表示で全文を確認できるようにする。hoverだけに依存しない。
- `fmtAvg`、`fmtIP`、`fmtSal` 等の既存フォーマッタと集計処理を再利用する。見た目を揃えるために、投球回・勝率・打率の計算をUIへ再実装しない。
- 未記録、算出不可、対象外、読み込み中、実測0を区別する。実測の防御率0.00や勝率1.000を欠損扱いにしない。`value || '---'` のように有効な0を失うフォールバックを新設しない。
- `---` / `—` など現行の欠損表記は、意味を説明したうえで画面内を揃える。見た目だけを理由に保存値や全画面の表記を一括変換しない。分母・対象打球数など算出条件が不足する場合は、0を補って値を作らない。
- 年度、投手／野手、対象球団、規定到達などの比較条件と並び順を示す。並べ替えがある表では、操作名と現在の方向を分かるようにし、欠損と0の扱いを検証する。

## 7. 操作・状態・アクセシビリティ

- 主なタップ操作は高さ44px以上、アイコンだけの操作は44×44px以上を本プロジェクトの基準にする。見た目のアイコン寸法とタップ領域を混同しない。入力や選択はラベルを持たせる。
- 操作は `button`・リンク・`select` 等の意味に合う要素を使う。選択フィルタの `aria-pressed` と本来のタブUIを区別し、ARIA属性だけを追加して操作を未実装にしない。
- 進行・保存・交渉等の実行中は、既存の状態に合わせて二重操作を防ぎ、処理中と完了を区別する。無効な操作は理由や次の行動を近くに示す。UI変更だけで進行可否の判定を置き換えない。
- 空状態は「まだ試合がない」「候補がいない」等の理由を示す。エラーは起きたことと再試行・戻る等の手段を示し、保存成功や処理完了を先に表示しない。
- ダイアログでは名称、閉じる手段、Escape、Tab／Shift+Tab、起点へのフォーカス復帰、背景スクロールを確認する。破棄してよいかの判断が必要な編集では、無条件に閉じて変更を失わせない。
- キーボードのフォーカスを消さず、下部ナビやsticky領域の陰へ隠さない。拡大表示・長文・縦横切替でも重要な情報と操作が失われないことを確認する。

## 8. 作業手順と受け入れ条件

1. 最新mainと対象ルートを確認し、「何を判断・操作しやすくするか」「変えないもの」を短く整理する。既存の共通部品・対象CSS・データの出所を確認する。
2. DES-01では代表モックA（ホーム＋試合結果）、B（オフシーズン編成計画＋交渉）、C（選手分析・ランキング）の構造・部品を承認してから、配色・トークン・ナビを確定し後続画面へ展開する。青写真の「ホーム／編成／日程／分析／経営」5タブ・年間フェーズ帯・共通領域・全画面構成は提案であり、現在のナビを変更する指示ではない。合意済みの案や小修正はその範囲を直接実装し、毎回の新規モックや再承認を必須にしない。
3. 一つの画面・操作フローから変更する。ゲームロジック・永続化・物理演算・依存追加・全体CSS再編を混在させない。
4. 同じデータ・年度・日付・選択条件で変更前後を確認する。乱数を含む画面は同じseedや再現可能なテスト状態を使い、安定した比較を行う。

### 画面確認

変更に関係する通常・未記録・実測0・空・読み込み中・エラー・無効状態も確認する。存在しない状態をテスト目的で本番ロジックへ作り足さない。スクリーンショットだけで操作確認を代替しない。

### 自動検証と報告

検証は [docs/TEST_STRATEGY.md](./TEST_STRATEGY.md) と [AGENTS.md](../AGENTS.md) の3段階運用に従う。開発中は変更に直結したテスト、PR品質ゲートは同一コミットのCI（ビルド・全Vitest・中核E2E）、大規模移行／リリース前は全E2Eを使用する。Work側で同じ全セットを理由なく再実行しない。文書のみの変更は参照リンク・方針の整合・差分範囲を検証し、ローカルのビルド・単体・E2E再実行と画面確認は不適用とする。CI設定は変更せず、実際の実行状況を記録する。コマンドは [package.json](../package.json) と [CONTRIBUTING.md](../CONTRIBUTING.md) を確認する。[playwright.config.js](../playwright.config.js) の現行 `mobile-webkit` は進行smokeの `E1 new game` に限定される。CI成功を全画面のWebKit検証済みと解釈しない。

PRには次を記録する。

- 対象画面、改善する判断・操作、再利用した部品・スタイル、基準からの例外と理由。
- 対象コミット、表示寸法、ブラウザ、再現条件を伴う変更前後の画像。取得できない場合は「未検証」と理由を明記する。画像はPR添付や参照可能な成果物に置き、消える作業ディレクトリだけを根拠にしない。
- 実行コマンドと結果、操作・フォーカス・consoleの確認結果。既存失敗と今回の失敗を区別し、未実行・不適用は成功と分ける。

ビルド・単体テストの成功や過去の `design-qa.md` は、今回の目視・操作確認の代わりではない。環境上確認できない項目があってもコードや文書の作業は進められるが、実画面検証済みと報告しない。文書のみのPRでは画面検証を不適用と記録し、参照先・変更範囲・矛盾の有無を確認する。
